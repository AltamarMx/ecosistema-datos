¿Qué significa reproducible?

Reproducibilidad

Mismos datos + mismo código + mismas condiciones → mismo resultado.

Es lo que hoy está en juego.

Replicabilidad

Misma pregunta, datos nuevos → resultados consistentes.

Es otro problema (más difícil).

La NASEM recomienda compartir datos, métodos y la descripción del entorno computacional.

National Academies of Sciences, Engineering, and Medicine (2019). Reproducibility and Replicability in Science. doi:10.17226/25303

Fijar términos antes de dar cifras: la literatura los usa de forma inconsistente. Hoy hablamos de reproducibilidad computacional: tus datos, tu código, ¿mi máquina obtiene lo mismo? “Describir el entorno computacional” = lo que uv.lock hará en el bloque 2.

uv: el entorno es un archivo

🖐 Práctica · 15 min

¿Qué es un ambiente virtual?

Una carpeta (.venv/) con su propio Python y sus propios paquetes, aislada del resto de tu computadora.
Cada proyecto tiene el suyo.

🧊 Sin ambiente: el refri compartido del depa

  • “¿Quién se acabó mi leche?” → otro proyecto actualizó numpy y el tuyo truena.
  • “Ese yogurt es de 2019” → paquetes viejos que nadie se atreve a borrar.
  • “No toques lo del casero” → sudo pip install rompe el Python del sistema.
  • “En mi refri sí había” → “en mi máquina sí funciona”.

🍱 Con ambiente: tu lonchera con tu nombre

  • Cada proyecto, su .venv/: nadie más mete la mano.
  • Lo que lleva está escrito: uv.lock.
  • Otra persona arma la misma lonchera: uv sync.
  • ¿Ya no la usas? Borras la carpeta y listo.

Con uv no lo activas ni lo administras: uv run lo crea y lo usa por ti.

Dejar que se rían con el refri: todos lo han vivido. Luego mapear cada chiste a un error real. Dato para quien ya lo vio: en macOS y Linux recientes, pip fuera de un ambiente responde “externally-managed-environment”: el sistema mismo ya te pide un ambiente virtual.

“En mi máquina sí funciona”

Antes: muchas herramientas

  • pyenv para versiones de Python
  • venv / virtualenv para entornos
  • pip para instalar
  • pip-tools para fijar versiones
  • pipx para herramientas
  • requirements.txt… sin versiones

Ahora: una sola, uv

  • Instala Python por ti
  • Crea y sincroniza el entorno
  • Agrega dependencias y las fija en uv.lock
  • Ejecuta dentro del entorno
  • Muy rápido (escrito en Rust, de Astral)

El escalón 2 del embudo —“no se pueden instalar las dependencias”— es el que uv elimina.

Conectar con el embudo: la mayoría de los notebooks ni siquiera se pudo instalar.

Versionado: qué es git y por qué importa el diff

🖐 Práctica · 15 min

¿Qué es el versionado?

  • Todos hemos versionado a mano: tesis_final_por_fin_eso_espero.docx.
  • Copias con nombres… sin autor, sin fecha, sin motivo.
  • Y la pregunta clave no tiene respuesta: ¿qué cambió entre una y otra?

El meme hace el trabajo: todos reconocen esa carpeta.

git: un archivo, toda su historia

$ git log --oneline
a41c9e2 Barrido: absortancia 0.2–0.8, h 5–20
7d03b1f ghi_diaria: prueba con respuesta conocida
c2e8f50 Datos 2024-10 → 2026-10 a Parquet
91fa3d4 PLAN.md firmado
0b7e2aa uv init
  • Un commit es una foto del proyecto con autor, fecha y mensaje.
  • Cada commit es un punto de retorno: equivocarse deja de ser caro.
  • git es el versionador (software libre). GitHub es la plataforma que lo hospeda: respaldo y colaboración, gratis para la academia (GitHub Education).

Precisión: git ≠ GitHub. Se puede usar git sin GitHub (y conviene saberlo).

Tres commits, una historia

git commit -m "Proyecto inicial con uv"
git commit -m "io.py: crudos de ClimaLab a Parquet"
git commit -m "ghi_diaria() con prueba de respuesta conocida"

0b7e2aa Proyecto inicial con uv lun 10:02 · + pyproject.toml, uv.lock

c2e8f50 io.py: crudos de ClimaLab a Parquet mar 17:40 · + src/climalab/io.py

HEAD · estás aquí 7d03b1f ghi_diaria() con prueba de respuesta conocida jue 12:15 · + tests/test_radiacion.py

¿ … ? tu próximo cambio

Cada punto es una foto completa del proyecto: puedes compararlas (git diff 0b7e2aa 7d03b1f) o volver a cualquiera.

Señalar de izquierda a derecha: cada commit guarda quién, cuándo, qué y por qué. El mensaje es para tu yo de dentro de seis meses. HEAD = dónde estás parado.

El ciclo básico

  editas archivos ──► git add ──► git commit -m "por qué" ──► git push
   (directorio)       (preparas)     (foto en la historia)     (GitHub)
        ▲                                                         │
        └──────────── git diff: ¿qué cambió desde la última foto? ┘


  • git status: qué está modificado.
  • git diff: qué cambió exactamente, línea por línea.
  • git log: la historia.
  • git restore archivo / git revert <commit>: volver atrás.

Lo mínimo indispensable. Branches y merge quedan fuera: hoy solo historia y diff.

Leer el diff: la unidad de revisión

El diff es la lista exacta de lo que cambió: líneas que salen (-) y líneas que entran (+). Con agentes es el instrumento de revisión: no relees todo, lees el cambio.

$ git diff src/climalab/radiacion.py

 def ghi_diaria(ghi_w_m2):
     """GHI diaria en kWh/m² por día."""
-    wh = ghi_w_m2 * (1 / 60)               # cada muestra [W/m²] dura 1 min
-    return wh.resample("1D").sum() / 1000
+    return ghi_w_m2.resample("1D").mean() / 1000
  • El agente “simplificó”… y cambió sum() por mean(): ya no es energía diaria [kWh/m²·día], es potencia promedio [kW/m²].
  • Corre sin error, el número parece razonable: solo el diff lo delata.

Caso ficticio pero típico. Dos líneas rojas y una verde: leerlas toma veinte segundos. Esta función vuelve en el bloque 6 con una prueba que también lo habría cazado.

De Jupyter a marimo

👀 Exposición · 15 min

Lo que Jupyter resolvió… y lo que dejó pendiente

Resolvió

  • Código, texto y resultados juntos
  • Exploración interactiva
  • Una forma de contar el análisis

Dejó pendiente

  • Estado oculto: la memoria no coincide con lo que ves
  • Celdas ejecutables en cualquier orden
  • .ipynb = JSON + resultados → diff ilegible
  • Dependencias no declaradas
  • No importable: el código queda atrapado

Recuerda: 24 % corre, 4 % reproduce (Pimentel et al., 2019).

Jupyter fue una revolución y lo sigue siendo para enseñar. El problema no es la idea del notebook, es el modelo de ejecución y el formato del archivo.

El estado oculto, en cuatro celdas

[1]  umbral = 40                         # °C
[2]  calientes = df.filter(pl.col("tsa") > umbral)
[3]  umbral = 35                         # "probemos con 35"…
[ ]  fig = graficar(calientes)           # ¿con 35 o con 40?
  • La celda [2] no se volvió a ejecutar: calientes sigue calculado con 40.
  • Si borras la celda [1], umbral sigue en memoria.
  • El archivo guardado dice 35; la figura se hizo con 40. Nadie lo nota.

marimo: el notebook como grafo reactivo

import marimo

app = marimo.App()

@app.cell
def _():
    import marimo as mo
    import polars as pl
    return mo, pl

@app.cell
def _(mo):
    umbral = mo.ui.slider(30, 50, value=40,
                          label="Umbral [°C]")
    umbral
    return (umbral,)

@app.cell
def _(df, pl, umbral):
    calientes = df.filter(pl.col("tsa") > umbral.value)
    return (calientes,)
  • Cada celda declara lo que usa y lo que define.
  • Cambias umbral → se re-ejecuta todo lo que depende de él.
  • Borras una celda → sus variables desaparecen.
  • Una variable se define en una sola celda.
  • El archivo es Python puro: diff limpio en git.

No hace falta escribir ese formato a mano: el editor lo genera. Lo que importa es que el archivo es texto, ordenado por dependencias, y legible en un diff.

Un archivo, cuatro usos

Comando
Editar (notebook reactivo) uv run marimo edit exploracion.py
Ejecutar como script uv run python exploracion.py
Servir como app (oculta el código) uv run marimo run exploracion.py
Exportar a HTML que corre en el navegador uv run marimo export html-wasm exploracion.py -o sitio/


  • Las funciones de un notebook marimo se pueden importar desde otro código.
  • La app con sliders reemplaza muchos casos en los que antes hacía falta un framework web.

“Como app” = el mismo archivo, sin tocar código. Para compartir con alguien que no programa.

  • Sigue siendo reactivo y en .py: lo que la IA escribe se ve en el diff.

Vamos a contar una historia con datos de la mano de un LLM como agente

👀 Demo · 8 min

El modelo, solo

  tú ──── texto ────►  ┌────────┐
                       │ modelo │
  tú ◄─── texto ─────  └────────┘
  • Texto entra, texto sale.
  • No ve tus archivos, no ejecuta nada, no sabe si su código corre.
  • Tú copias, pegas, ejecutas y le cuentas el error.
  • Tú eres el bucle.

Así usa la IA la mayoría: chat en el navegador. Útil, pero el humano hace todo el trabajo de ida y vuelta.

¿Qué es un agente?

Un agente es un LLM que trabaja en un bucle, con herramientas, hasta cumplir un objetivo.

   tu prompt · PLAN.md
            │
            ▼
   ┌──► propone una acción
   │            │
   │            ▼
 corrige   usa una herramienta
   ▲     (leer, escribir, uv run,
   │      quarto render …)
   │            │
   └─── observa el resultado
  • El LLM decide el siguiente paso; las herramientas le dejan actuar sobre archivos y terminal.
  • El bucle: propone → ejecuta → observa → corrige, hasta terminar.
  • Un chat te devuelve texto; un agente cambia tu proyecto y ve sus propios errores.
  • Multiplica la velocidad… y el daño si no hay reglas. Por eso todo pasa por git.

Definición mínima para la demo. La siguiente diapositiva separa las dos piezas: el modelo y el harness.

El harness: lo que convierte un modelo en agente

Harness permisos · contexto · memoria

Herramientas archivos · terminal · pruebas · MCP

Modelo

El harness (arnés) es el programa que envuelve al modelo. Decide:

  • Qué herramientas tiene y con qué permisos: ¿puede borrar? ¿pide confirmación?
  • Qué contexto carga: AGENTS.md, el plan, el repositorio.
  • Cómo maneja la memoria y las conversaciones largas.

Ejemplos: Claude Code, Codex CLI, OpenCode; también el asistente de marimo.

Idea central del bloque: lo que llamamos “la IA” son dos cosas separables, el modelo y el harness. Dos agentes con el mismo modelo se comportan muy distinto según su harness y su contexto.

Modelo ≠ harness: nube y local

Nube (p. ej. Claude, GPT, Gemini)

  • Modelos de frontera, los más capaces
  • Sin hardware propio; costo por uso
  • Los datos salen de tu máquina

Local (p. ej. Qwen vía MLX u Ollama)

  • Los datos no salen; sin costo por token
  • Exige hardware capaz (memoria unificada o GPU)
  • Rinde menos que la frontera

El mismo harness puede usar uno u otro motor: la decisión es por proyecto, no ideológica.

Nube para trabajo pesado; local cuando los datos no deben salir o para tareas acotadas.

Alternativa local: Ollama + OpenCode

  • Ollama corre el modelo en tu máquina; OpenCode es el harness, de código abierto.
  • OpenCode necesita un contexto de 64k o más: elige un modelo que quepa en tu memoria.
  • Mismo prompt, mismas reglas: OpenCode también lee AGENTS.md.
  • ollama launch abre también Claude Code o Codex con un modelo local: cambia el motor, no el harness.

Una vez: descarga el modelo y arranca Ollama con 64k de contexto

ollama pull qwen3.5
OLLAMA_CONTEXT_LENGTH=64000 ollama serve

En otra terminal, dentro de climalab/

ollama launch opencode

Fuente: docs.ollama.com (integración con OpenCode y context length). Probado: ollama 0.34 trae “ollama launch opencode”. Elegir un tamaño de modelo que quepa en memoria; con “ollama ps” la columna PROCESSOR debe decir GPU, no CPU. En la app de Ollama, el contexto se ajusta con el control deslizante en lugar de la variable de entorno. La diapositiva anterior (“Modelo ≠ harness”) ya planteó la decisión nube contra local.

AGENTS.md · las reglas

- Trabaja solo dentro de este repositorio;
  no leas ni escribas fuera de él.

# PLAN · Una semana en ClimaLab

## Objetivo
Contar qué pasó en la última semana:
temperatura y radiación.

## Datos
data/001_raw/ClimaLab.parquet (índice datetime)
tdb [°C] · ghi, dni, dhi [W/m²]

## Pasos
1. [x] analysis/ con un hola mundo
2. [ ] plotly, 2 subpaneles: tdb | ghi, dni, dhi
       última semana = 7 días hasta el último dato

## Criterios de aceptación
- uv run quarto render analysis/ sin errores
- git diff no toca data/001_raw/

Demo en vivo · 2 min · se firman con un commit

git add AGENTS.md PLAN.md && git commit -m "Reglas y plan para el agente"

Los dos archivos se llevan escritos; aquí se leen regla por regla y se firman con el commit. Cada regla corresponde a algo de hoy: uv (bloque 2), datos crudos intocables, Quarto (bloque 4). El plan fija lo que el prompt deja ambiguo: qué es “la última semana”. Claude Code: la versión instalada (2.1.306) debería leer AGENTS.md si no hay CLAUDE.md. Confirmarlo con /memory al iniciar; si no aparece, crear CLAUDE.md con la línea @AGENTS.md. AGENTS.md: el harness lo carga en cada sesión; sin él, el agente usa sus defaults (los de sus datos de entrenamiento). PLAN.md: se escribe antes de pedir una línea de código; su commit es la firma del contrato; es también la bitácora: qué propuso la IA y qué decidió la persona autora.

import pandas as pd
import plotly.graph_objects as go
from plotly.subplots import make_subplots

esolmet = pd.read_parquet("../data/001_raw/ClimaLab.parquet")
semana = esolmet.loc[esolmet.index.max() - pd.Timedelta(days=7):]

fig = make_subplots(rows=2, cols=1, shared_xaxes=True)
fig.add_trace(go.Scatter(x=semana.index, y=semana["tdb"], name="tdb"), row=1, col=1)
for col in ["ghi", "dni", "dhi"]:
    fig.add_trace(go.Scatter(x=semana.index, y=semana[col], name=col), row=2, col=1)
fig.update_yaxes(title_text="tdb [°C]", row=1, col=1)
fig.update_yaxes(title_text="[W/m²]", row=2, col=1)
fig.show()

Vibe coding vs. spec-driven

Vibe coding

  • El prompt es la especificación
  • El código no se lee
  • “Accept All”
  • Para proyectos desechables

Spec-driven

  • PLAN.md firmado es la especificación
  • El agente ejecuta; el humano escribe y verifica
  • Diff leído, pruebas pasando, commit
  • Para trabajo que se publica

Es la misma transición que está dando la industria del software con los agentes.

El bucle de trabajo

  un paso del PLAN ──► el agente escribe el .qmd ──► uv run quarto render
          ▲                                                  │
          │                                                  ▼
       git commit  ◄──── tú lees el diff ◄──── revisas la gráfica

Escribir AGENTS.md y PLAN.md exige saber programar y conocer las herramientas actuales. El agente rinde al nivel de quien lo guía.

Es el ciclo que acabamos de recorrer en los pasos 1 a 3. Nunca “hazme todo el análisis”: un paso del plan a la vez, diff corto. Si el agente propone pip install o un .ipynb, mejor: muestra por qué existe AGENTS.md.

Estrategia: paquetes que el agente usa con parámetros

Tú escribes y pruebas la física; el agente elige parámetros y combina.

  • La función es el contrato: nombre, parámetros con unidades, docstring y prueba.
  • El agente no reinventa el cálculo: lo llama con otros valores.
  • En el diff queda una llamada, no física nueva: se audita en segundos.
  • Instalable y versionado (uv add, uv.lock): persona o agente obtienen lo mismo.

Lo que tú escribes y pruebas

# src/climalab/modelo.py
def temperatura_sol_aire(tdb, ghi, a=0.6,
                         h=13.0, eps_dr=63.0):
    """Temperatura sol-aire [°C].
    a [-] · h [W/m²K] · eps_dr [W/m²]"""
    return tdb + (a * ghi - eps_dr) / h

Lo que le pides al agente

Con climalab.modelo.temperatura_sol_aire, barre la
absortancia de 0.2 a 0.8 y h de 5 a 20 W/m²K para la
última semana, y grafica las horas sobre 40 °C

Es la misma función del bloque 6. La idea: el conocimiento de dominio se empaqueta y se prueba una vez; el agente explora el espacio de parámetros. Lo que hay que revisar es qué valores eligió, no si la física es correcta. Puente: ¿y si el agente pudiera descubrir esas funciones por sí solo, en cualquier harness? Eso es MCP.

Explorar MCP: el concepto

  • Model Context Protocol: estándar abierto para conectar una aplicación de IA con herramientas y datos. Lo creó Anthropic en 2024; desde 2025 lo gobierna la Agentic AI Foundation (Linux Foundation), junto con AGENTS.md.
  • Participantes: el host (Claude Code, OpenCode, marimo…) abre un cliente por cada servidor.
  • Un servidor ofrece: tools (funciones que el agente ejecuta), resources (datos de contexto) y prompts (plantillas).
  • Descubrir y llamar: el agente pregunta qué herramientas hay (tools/list) y las invoca (tools/call).
 host: Claude Code · OpenCode · marimo
 ┌──────────────────────────────────┐
 │  cliente MCP       cliente MCP   │
 └──────┬──────────────────┬────────┘
        │ stdio (local)    │ HTTP (remoto)
        ▼                  ▼
  servidor "climalab"   servidor GitHub
  tools · resources · prompts

Tu paquete, envuelto en un servidor MCP, se vuelve una herramienta que cualquier agente descubre y llama.

Fuentes: modelcontextprotocol.io (arquitectura) y el anuncio de la Agentic AI Foundation (9 dic 2025). Solo el concepto: en esta charla no se construye el servidor.

Si la IA ya escribe código, ¿para qué aprender a programar?

El ecosistema, contra las causas

Dependencias no declaradas → uv · uv.lock · PEP 723 ✓

Sin historia → git · diff ✓

Estado oculto, orden de ejecución → marimo ✓

Datos pesados y sin tipos → Parquet ✓

Código atrapado en el notebook → src/ · paquete · pruebas ✓

Preprocesamiento no documentado → narrativa · PLAN.md ✓

El agente trabaja dentro de este ecosistema… si alguien lo construyó y se lo explicó.

Las pistas 🧭

  1. El documental — Python es una historia de personas que programan.
  2. uv — el agente usa pip si no sabes pedirle otra cosa.
  3. git — el diff solo sirve si sabes leer código.
  4. marimo — las herramientas nuevas eliminan clases enteras de errores.
  5. Parquet — el formato es una decisión técnica que nadie toma por ti.
  6. src/ — decidir qué es una función y qué prueba la valida es diseño.
  7. Agente — rinde al nivel de quien lo guía.
  8. MCP — solo usa tu conocimiento si lo empaquetaste.

Saber programar es la licencia de conducir

A

Auditar

Sin leer código no puedes revisar lo que el agente escribe: el diff es tu instrumento.

B

Entender

El criterio de dominio decide si el número es plausible (sum vs. mean); la IA no sabe lo que no le dijiste.

C

Guiar

El plan, las correcciones y la firma son humanas. La IA no firma.
